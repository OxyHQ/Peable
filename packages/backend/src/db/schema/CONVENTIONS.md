# Schema conventions

The binding ledger for Peable's PostgreSQL schema: what each decision is, and
why the obvious alternative is wrong. Read it before touching a table.

This schema is **greenfield**: nothing here carries a compatibility shape from
an earlier store, and every table follows the same conventions.

## Substrate

`drizzle-orm` over `postgres.js`, through `@oxy.so/db` — which owns the column
builders, the id generator, the casing authority (`DATABASE_CASING`), the
driver-error predicates, the migration ledger with its deploy-phase enforcement,
and the throwaway-database harness. Do not hand-roll anything that package
already provides; a second copy of a decision is a second copy to keep in sync.

**Extensions: NONE.** No geography, no text search, ids generated in the
application. `REQUIRED_EXTENSIONS` in `db/migrate.ts` states it as an explicit
empty list. An extension may **not** be added later by writing `CREATE EXTENSION
IF NOT EXISTS` into a migration: the duplicate-existence check short-circuits
before the privilege check, so that statement is a silent no-op where the
extension exists and a hard failure where it does not. Extensions are a database
prerequisite installed once by a privileged role.

## Ids

Every primary key is `text` holding a uuid v7, generated by the application
through `generatedId()`. The time component makes them k-sortable, so the
primary-key index stays append-mostly — which is also what lets the dashboard's
keyset pagination order by `id desc`.

**k-sortable is not ordered within a millisecond.** The 74 bits after the
timestamp are random, so two ids minted in one millisecond sort either way
about half the time. An `id` tiebreak is fine for a stable page walk and wrong
wherever the ORDER is the meaning — see §Provider event arrival order.

**`public_id` is a separate column, and the primary key is never the public
id.** Four tables carry a Stripe-parity external identifier (`merch_…`, `pi_…`,
`cs_…`, `link_…`) minted by `newId()`. It is `public_id` on all four, and `id`
always means the internal key. A serializer renders `id: row.publicId`.

**No foreign key ever points at an Oxy id.** `oxy_user_id`, `oxy_app_id`,
`sender_user_id`, `recipient_user_id` and `avatar_file_id` all belong to
another service's key space. They are enumerated in the `withoutForeignKey`
ledger in `db/__tests__/schemaGates.realdb.test.ts` with the reason, so an id
column nobody has decided about is a build failure rather than an absence.

## Closed value sets

`text` plus a CHECK derived from the SAME `const` tuple that types the column
(`schema/valueSets.ts`), never a pg `enum` — an enum puts the values in a type
whose every change is a migration and whose members cannot be removed at all.

Each tuple carries an `AssertAllListed` type alias, because `satisfies` alone
only proves each member IS a union member. The dangerous direction is the other
one: a union gaining a member no tuple lists type-checks everywhere and is then
refused by a CHECK on the first write of the new value, in production.
`schema/__tests__/valueSets.test.ts` covers what types cannot — the runtime
`PAYMENT_INTENT_STATUSES` array and the base-unit regex in another package.

### A bound parameter cannot appear in DDL

**Never interpolate a value into a `sql` template that becomes a constraint.** A
`${value}` in a drizzle `sql` template is a BOUND PARAMETER, and drizzle-kit
renders it into the migration as the literal text `$1`; a CHECK cannot carry
one, so the migration fails at apply time. `tsc` is clean and `drizzle-kit
generate` reports success, so nothing before the apply catches it. Measured
here: the first generated migration contained `CHECK (next_derivation_index >=
$1)` the moment a bound became a named constant instead of a literal typed into
the template. Use `sql.raw(...)` with the value interpolated into the STRING.
`db/__tests__/schemaGates.realdb.test.ts` fails the build on any `$<digit>` in a
migration.

## Money

`amount` is `text` holding a canonical base-unit integer string, with a CHECK
matching `isBaseUnitString`'s own pattern exactly.

Not `bigint`: postgres.js decodes `int8` as a STRING anyway, and an `int8`
ceiling is not the domain's — the application works in JS `bigint`, which is
unbounded. `text` keeps the wire representation byte-for-byte and the CHECK
supplies the validation. The CHECK refuses a leading zero, so
one amount has exactly one spelling.

## Counters, and why they are `integer`

A wrong derivation index is not a wrong number on a screen. It is money at an
address the recipient cannot spend from, or two payers sharing one address the
gateway can then attribute to neither. That is the standard every decision in
this section is held to.

`social_receive_cursors.next_derivation_index` — the ONE counter every FairCoin
address comes from since ADR 0021 D5 (social, merchant and seller payments) —
is `integer`, and that is the domain rather than a size guess: a non-hardened
BIP32 child index is bounded by 2^31 − 1, exactly `int4`'s ceiling.

**Verified against both derivation paths, not assumed.** `@fairco.in/core`
exports `MAX_SOCIAL_RECEIVE_INDEX = HARDENED_OFFSET - 1` and `assertValidIndex`
refuses anything above it (`2147483647`). `db/__tests__/derivationIndexBound.test.ts`
pins the agreement, by CROSSING the boundary rather than by comparing a constant
against itself, and fails the build if the derivable space ever widens — at
which point `integer` would silently start refusing legal indices.

Two consequences, both wanted:

- Exhausting it raises `22003` and REFUSES the reservation, instead of wrapping
  to an index already handed out — an address that already has a payment on it.
- The value comes back as a JS `number`. A `bigint` column would make it a
  string, so `index + 1` would be CONCATENATION (`"0" + 1 === "01"`) and derive a
  completely different address. Pinned by two consecutive reservations in
  `db/__tests__/socialReceiveCursor.realdb.test.ts` (and through the payment
  path in `connectedAccountFaircoin.realdb.test.ts`); one reservation cannot
  tell a number from a string that prints the same.

### An address is handed out once, for ever (ADR 0021 D9, amended 2026-11-06)

`payment_intent_outputs (network, address)` is unique, full — not partial: an
address belongs to ONE output for ever (migration 0114 dropped the recycling
columns `recycled_at`, `retired_at`, `recycle_checked_at`, `recycle_lease_until`
and made the index full again; until 2026-11-06 a cancelled payment's unused
address could be handed to a later payment, and a late payer of the old quote
then paid the new order). `social_send_attributions (address, network)` is
unique as before. There is no cross-table unique index; instead every
reservation derives the next index's address and skips it when either table
already holds it (`reserveFreshAddress`, `services/faircoin/addressPool.ts`) —
possible only where history left a cursor behind an address it derived
(migration 0009). `derivation_index` (NULL only on outputs written before 0105,
CHECKed `>= 1`) is what the wallet derives and signs with.

The two tables ARE the recipient's watch set: `GET
/v1/social/me/receive_addresses` reads their union by
`(recipient, network, derivation_index)` (`*_recipient_index_idx`), and the
per-recipient daily bounds count by `(recipient, network, created_at)`
(`*_recipient_created_idx`). No third table copies them.

### The cursor's index is the wallet's sync cursor (ADR 0021 D9)

`social_receive_cursors.next_derivation_index` has no ceiling any more (the
`WHERE` of the upsert's `DO UPDATE` that refused `≥ 1 980` is gone with the
contiguous watch window). What it does carry is ORDER: the upsert's row lock is
held until the reserving transaction ends, and the address's own row (the
output, or the attribution) is written in that transaction, so for one account
and network an index commits only after every lower one has committed or rolled
back. That is why a wallet that has synced through index `n` misses nothing by
asking for `> n`, and why both writers MUST record the address in the
reservation's transaction — an attribution written after the reservation
committed (as it was until 2026-11-06) could appear below a cursor a wallet
already passed. Migration 0113 moved every cursor above the indices already
recorded for its account, so this holds for older rows too.

## Composite foreign keys carry the invariants a CHECK cannot

A CHECK sees one row of one table. Three rules here span two tables, so they are
expressed as composite references instead:

- `payment_intents (merchant_id, network) → merchants (id, network)`. This is
  the network firewall — `createIntent`'s `NetworkMismatchError` — in the one
  form no future code path can route around. Its implicit `ON UPDATE RESTRICT`
  additionally means a merchant's network cannot change out from under an intent
  that already exists.
- `checkout_sessions` and `payment_links` each reference `merchants (id,
  oxy_app_id, environment, network)`. Those three fields are denormalized from
  the merchant at creation time; carried by the reference, they are the
  merchant's values or the row does not exist.

**The targets must be `unique()` table constraints, not `uniqueIndex()`.**
drizzle-kit emits every `ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY` BEFORE every
`CREATE UNIQUE INDEX`, so a foreign key pointed at a unique INDEX fails to apply
with `42830 there is no unique constraint matching given keys` — the target does
not exist yet at that point in the file. Measured against a real server; `tsc`
and `drizzle-kit generate` are both clean either way.

**And `unique()` is not enough once the table already exists.** The rule above
works because a `unique()` constraint is emitted INSIDE its `CREATE TABLE`. Add a
new unique target to a table that is already there and it becomes its own
`ALTER TABLE … ADD CONSTRAINT … UNIQUE` — which drizzle-kit again orders AFTER
every foreign key, including the ones pointing at it. MEASURED on PostgreSQL
16.13 while adding `merchants_id_oxy_app_id_environment_key` in `0001`:

```
ERROR:  there is no unique constraint matching given keys for referenced table "merchants"
```

There is no drizzle-kit knob for this. **Move the `ADD CONSTRAINT … UNIQUE`
above the foreign keys by hand in the generated `.sql`, and say in a comment
that you did and why** — `0001_certain_skin.sql` is the worked example. This is
the one kind of hand edit a migration may carry; renaming the file, editing
`meta/_journal.json` and hand-writing a snapshot are still forbidden. Apply it
against a real server before committing: nothing earlier in the pipeline fails.

### A NULL in a composite reference switches the whole reference OFF

`network` is nullable, because a card intent has no network (ADR 0001 D1/D6).
That interacts with the two references above in a way nothing in the schema
shows, so it is written down here.

A composite foreign key defaults to **`MATCH SIMPLE`**, which is satisfied with
**no check performed** as soon as ANY referencing column is NULL. That is the
semantics wanted — the network firewall binds a FairCoin intent and is vacuous
for a card one — and it means the reference stops constraining its OTHER columns
too. The composite reference was the only thing pointing `payment_intents.merchant_id`
at `merchants`, so a card intent could name a merchant that does not exist.
MEASURED, PostgreSQL 16.13:

```
-- (merchant_id, network) → merchants(id, network), network NULL
insert into intents values ('i4','ghost-merchant',null);
INSERT 0 1                     -- accepted; no referential integrity at all
```

**So every composite reference whose nullable column may be NULL carries a
narrower companion reference over the columns that are always present:**

- `payment_intents (merchant_id) → merchants (id)`, beside the
  `(merchant_id, network)` firewall.
- `checkout_sessions` / `payment_links` `(merchant_id, oxy_app_id, environment)
  → merchants (id, oxy_app_id, environment)`, beside the four-column identity
  reference. Without it, a card session's denormalized `oxy_app_id` and
  `environment` stop being guaranteed the moment `network` is NULL.

With both present the FairCoin firewall still refuses a wrong network, the card
row still cannot name a ghost merchant, and a card session still cannot claim
the wrong `environment` — all MEASURED.

**`MATCH FULL` is the obvious alternative and is wrong.** It demands
all-or-nothing nullity across the referencing columns, and `merchant_id` is NOT
NULL, so it refuses every card row. MEASURED:

```
ERROR:  MATCH FULL does not allow mixing of null and nonnull key values.
```

The rail's own requirement is a CHECK, not a reference, because it is one row of
one table: `rail <> 'faircoin' OR (address IS NOT NULL AND network IS NOT NULL)`.

### A firewall that must bind SOME rows reads a GENERATED column (ADR 0012)

A payment made ON BEHALF of a seller carries the SELLER's network, and its
platform may have none (a card-only platform). The merchant firewall
`(merchant_id, network) → merchants (id, network)` would refuse every such row.
It now reads `merchant_network`, a STORED GENERATED column
`CASE WHEN connected_account_id IS NULL THEN network END`: identical to
`network` on every direct row, so the firewall binds exactly as before, and
NULL on an on-behalf row, so `MATCH SIMPLE` switches it off there. The
on-behalf row is held instead by `(connected_account_id, merchant_id, network)
→ connected_accounts (id, merchant_id, network)` — the account is THIS
platform's and the network is the ACCOUNT's — plus its network-free companion.
`checkout_sessions` carries the same pair.

Why generated rather than a column the application writes: the CASE is the
rule, and a column every writer had to remember would be one more thing that
could disagree with `connected_account_id`. A generation expression may only
name its own table's columns, so it is written as raw SQL (`sql.raw`), not
through drizzle column references. Adding one REWRITES the table under an
ACCESS EXCLUSIVE lock — say so in the migration.

## `ON DELETE`

Decided per relation, never defaulted:

- `restrict` on everything in the money graph. A merchant with payment history
  cannot be deleted, and losing the money record is never the right consequence
  of removing a party. Nothing deletes any of these today; `restrict` states what
  would happen rather than leaving it to whoever writes that statement.
- `cascade` on `events.payment_intent_id`, `webhook_deliveries.event_id` and
  `webhook_deliveries.endpoint_id`. An event about a payment, and a delivery of
  an event to an endpoint, are derived records with no meaning without what
  they derive from; the 30-day event sweep and an endpoint's deletion rely on
  the cascade to take the deliveries with them.
- `set null` on `recurring_observation_outbox.event_id`: the relay's own record
  is `relayed_at`, which outlives the swept event.
- `cascade` on `idempotency_keys.merchant_id`, for the same reason: a stored
  answer is derived from a request to that merchant, lives 24 hours, and is
  not part of the money graph.

## CHECK constraints that were considered and REJECTED

An empty table makes almost any constraint expressible, which is exactly why
each one has to be checked against every writer first. Three that look obvious
and are wrong:

- ~~**`livemode ⇔ environment = 'production'`** would refuse the registration
  of every production merchant. Nothing writes `livemode`; every row carries the
  default.~~ **NOW PRESENT** (`merchants_livemode_agrees_check`, migration
  `0011`). The observation was accurate and the conclusion was backwards: a
  published field that participates in no decision and reads `false` on every
  production merchant is not a harmless default, it is the wire contract saying
  something untrue. The fix was to give it a writer — `insertMerchant` derives
  it from `environment` — which makes the constraint correct rather than
  impossible. The migration is `post` and carries a backfill, because the
  outgoing image still writes `false` for every environment and the constraint
  cannot land while it serves.
- **`expires_at > created_at`** compares an application clock against a database
  default and would fail on skew, for no invariant anyone depends on.

(The `(webhook_url IS NULL) = (webhook_secret IS NULL)` question went away
with the columns: a webhook endpoint's url and secret are both `NOT NULL`.)

Two that ARE there, because every writer was checked:

- `payment_intents_processing_requires_txid_check` (was `…_broadcast_requires_txid_check`
  before ADR 0019). A FairCoin `processing` or `succeeded` intent has a txid:
  `submit_tx` is the only path to a chain `processing` and sets `txid` in the
  same write, and `succeeded` is reached only by the settlement watcher, which
  selects on `txid` being present. `canceled` is deliberately outside the set —
  an expired intent has no txid and an underpaid one has one.

  **This CHECK also decides which fixture can test the code around it.** A
  mutation survived here: dropping `isNotNull(txid)` from `findWatchableIntents`
  left the suite green, because every txid-less fixture was excluded by the
  STATUS predicate before the txid predicate was reached. A txid-less
  `processing` FairCoin row is UNREPRESENTABLE, so the discriminating fixture is
  a `canceled` one — the only status that holds rows both with a txid
  (underpaid) and without (expired). Narrowing the constraint later would
  silently remove it.
- `webhook_deliveries_status_agrees_check`. `delivered` and `last_status` are two
  spellings of one fact and both writers derive the second from the first; the
  CHECK is that derivation, where the two cannot come apart.

### The three on `social_send_attributions`' source columns

`source_app` / `source_ref` say what a social payment was for — which app the
payer was in, and that app's own id for the thing. Both are **nullable and never
defaulted**: most social payments are one person paying another for nothing in
particular, so NULL means "no app said", which is a fact, where a default would
be a claim the recipient reads as if the payer had made it.

The writer is one function — `insertSendAttribution`, reached only from
`POST /v1/social/:username/next_address` — and all three CHECKs were checked
against it:

- `…_source_ref_needs_app_check`. A `ref` means something only inside the app
  that minted it, so a ref with no app names nothing anybody can resolve. The
  route parses the two together inside one `source` object whose `app` is
  required, and `InsertAttributionParams` takes that same object rather than two
  loose strings, so the half-filled state is not expressible above the database
  either.
- `…_source_app_length_check` / `…_source_ref_length_check`. The bounds the
  route's zod schema validates (`SOCIAL_SOURCE_APP_MAX_LENGTH` and
  `SOCIAL_SOURCE_REF_MAX_LENGTH`, imported from `@peable.to/shared-types` by
  BOTH, so the request and the table cannot drift), restated where they are true
  of the data. This is the money CHECK's argument applied to a different risk:
  `source_ref` is deliberately **opaque** — nothing in this repository parses,
  resolves, joins or indexes it — so nothing downstream would ever notice it
  growing, and an unbounded column nothing reads is how a display hint becomes
  somewhere to stash a payload.

All three are `<column> IS NULL OR …`, which is why `0010` can add them in the
same `pre` migration as the columns: they are vacuous for every row an image
that predates them writes.

### Constraints added for the card rail's own failures

Each of these exists because a specific defect reached production-shaped code,
and each was checked against every writer first.

- **`merchants_network_present_check`** (was `merchants_chain_fields_agree_check`,
  ADR 0021 D5) — every merchant has a FairCoin network, its environment's,
  because every order offers FairCoin; there is no key beside it any more (the
  owner's Peable wallet receives), so the old *network ⇔ xpub* pair is gone.
- **`refunds_origin_ref_agrees_check`** — `(origin = 'merchant') = (external_ref
  IS NOT NULL)`. A refund created at the acquirer (a dashboard refund, or the
  network resolving a dispute) has no merchant reference and cannot be given
  one. The two columns are written by different paths — the route writes the
  first, the event drain the second — and a drift is silent in both directions:
  a merchant refund with no reference is un-retryable, and an imported one
  carrying a reference claims the merchant asked for a refund they never made.
  The unique index on `(merchant_id, external_ref)` is PARTIAL for the same
  reason; NULLs are distinct in Postgres so an unpartitioned one would also
  work, and the `WHERE` says what is being promised.
- **`transfer_reversals_*`** — the table exists because an AMOUNT IS NOT AN
  IDENTITY. The reversal service derived its provider idempotency key from
  `trr:<transfer>:<amount>`, so two distinct reversals of one transfer for the
  same amount presented one key and the provider answered the first to the
  second request. The rows are NOT summed to produce
  `transfers.amount_reversed`: that column holds the PROVIDER's cumulative
  figure, which includes reversals this gateway did not make, and a sum here
  would be a second answer to one question.
- **`payment_intents.provider_charge_id`** is a SECOND provider id beside
  `provider_object_id`, not a duplicate. A payment and the charge it produces
  are different objects, and a transfer's `source_transaction` names the charge
  — passing the payment's `pi_…` makes the provider answer `No such charge`, so
  every multi-seller settlement fails at the provider and reads as an outage.
  The `faircoin_has_no_provider` CHECK gained it as a third conjunct.

## A rule a CHECK cannot express lives at ONE write chokepoint, and losing it is silent

A drizzle schema has no hooks. A rule that the database cannot express is true
only of writes that go through one function, and NOTHING fails when it is
dropped.

The instances here: who RECEIVES a FairCoin payment is decided in ONE module,
`services/faircoin/recipient.ts` (the owning account's or the seller's Peable
wallet, ADR 0021 D5), and a seller's FairCoin half is confirmed by ONE writer,
`confirmFaircoinHalf` (`db/accounts/connectedAccountRepository.ts`), reached
only from the seller's own Oxy session. Neither is expressible as a CHECK — the
first needs a DID read, the second a session — so each is a single chokepoint
with a test that would fail without it (`faircoinConnect.realdb.test.ts`,
`connectedAccountFaircoin.realdb.test.ts`).

The xpub firewall (`assertWatchOnly`) that used to be this section's example is
retired with the key: no column holds a private or extended key (only the
PUBLIC identity key each FairCoin address derives from, ADR 0002).

## Protected columns

`db/protectedColumns.ts` withholds `webhook_endpoints.secret` /
`previous_secret` from every ordinary read, at the TYPE level.
`client_secret` is deliberately NOT in the registry: it appears in a DTO by
design, so listing it would not withhold anything — it would only make every
read name it explicitly, which is the opposite of a guard.

## Timestamps

`created_at` and `updated_at` are `timestamptz` from `@oxy.so/db`, defaulted at
millisecond precision (a `timestamptz` carries microseconds and a JS `Date` does
not, which silently breaks any keyset built on one). `updated_at` is maintained
by the application through drizzle's `$onUpdate` — so it fires on `db.update()`
and on an `ON CONFLICT DO UPDATE` branch, and NOT on a raw `db.execute(sql\`update
…\`)`. `social_receive_cursors` carries both columns.

## Provider event arrival order

The drain applies `provider_events` oldest first, and for two events about one
object the order IS the meaning: a dispute's `created` before its
`funds_withdrawn`, or the merchant is told "created" by the wrong event and
never told the funds moved. `created_at` is millisecond precision and such
pairs routinely share a millisecond, so the tiebreak decides — and it used to be
the uuid v7 `id`, which inverted about half of them (§Ids).

`received_seq` is the tiebreak: `bigint`, `NOT NULL`, defaulted to
`nextval('provider_events_received_seq')` — numbered by the database at insert,
never by the application. Decisions a reader would otherwise undo:

- **A sequence default, not `GENERATED … AS IDENTITY`.** Adding an identity (or
  any volatile default) in `ADD COLUMN` rewrites the hot table under ACCESS
  EXCLUSIVE; a bare `ADD COLUMN` plus `SET DEFAULT` are both catalog-only
  (`0069`), and identity cannot be attached to a nullable column at all.
- **`CACHE 1`, stated in the schema.** A cached sequence hands each session its
  own block, so two ingress connections would number interleaved deliveries out
  of order.
- **`bigint` is safe here only because it is never READ.** It appears in
  `ORDER BY` and nowhere else — not in `EVENT_COLUMNS`, not on a DTO — because
  postgres.js decodes `int8` as a string (§Counters). `mode: 'bigint'` makes the
  query builder hand back a JS `bigint` if anything ever does select it.
- **The rows that predate it are NEGATIVE** (`0070`, `-N … -1` by `created_at,
  id`): the running image's inserts were already taking 1, 2, … from the
  default, and every older row arrived before them.
- **`NOT NULL` arrives in four steps** (`0069` DDL alone, `0070` backfill, `0071`
  the CHECK `NOT VALID`, `0072` post: validate, `SET NOT NULL` without a scan,
  drop the CHECK). The CHECK comes after the backfill because a `NOT VALID`
  CHECK is still enforced on every UPDATE, and the running drain updates
  pre-`0069` rows.
- **Arrival order, not per-object serialization.** Stripe does not promise
  delivery order, so most handlers already read the truth rather than trust the
  sequence: intents reconcile with the provider, refunds read the refund's
  state, accounts re-read, transfers take the provider's cumulative total. The
  defect was the drain reordering events that DID arrive in order. Holding an
  object's later events behind an earlier failure would let one event left
  failed for an operator by design starve every later event about that payment.

## Testing

Every database property is tested against a REAL Postgres server, one throwaway
database per test file, created and migrated through `db/migrate.ts`'s own `main`
rather than a second composition of `runMigrations`. A mocked `db.insert()`
accepts any statement, including one the server rejects — so a CHECK, a unique
index, a row lock and the driver's decoding of an `int4` have no mocked
counterpart at all.

The suites skip when `TEST_DATABASE_URL` is unset, so a developer without a
container is not blocked — and `schemaGates.realdb.test.ts` turns that skip into
a RED build when `CI` is set, because a skipped suite and a passing suite are
indistinguishable in a summary line.


## Organization contributions

`payment_links.contribution` is the immutable, schema-validated contribution
configuration: the opaque Oxy organization reference, purpose, fixed/free policy
and optional UTC expiry. The Oxy account remains external; no membership or
organization content is copied. Its operation key is unique per merchant and
never appears in a DTO. A fixed link has a positive amount; a free link stores
zero as a policy sentinel and every minted intent has a positive payer-chosen
amount. The contribution shape CHECK restricts this phase to the FairCoin rail.

`payment_intents.payment_link_id` is a local nullable FK with RESTRICT deletion,
set during intent creation so collection reports never infer ownership from
mutable metadata. Existing non-link intents remain NULL. The keyset collection
query scopes both merchant and link; `payment_intents_payment_link_id_idx`
supports it. No contribution-specific payment state or webhook producer exists:
the existing FairCoin state machine, CAS transition and outbox remain authoritative.


## Oxy Files (ADR 0043)

`oxy_file_reference_syncs`, `oxy_file_events`, `merchant_avatar_audit` and
`oxy_file_reconciliation_runs` (`schema/oxyFiles.ts`) are Peable's side of Oxy's
file references. Decisions a reader would otherwise undo:

- **A sync row is keyed by the reference, not by an operation.** Its primary key
  is `(file_id, entity_type, entity_id)` — Oxy's own reference identity — and the
  loop decides add-or-remove from the database at the moment it acts. An
  add/remove log would replay a set-clear-set in whatever order it was retried
  and could end with the reference gone while the avatar is set. `version` is the
  compare half that keeps a change made during a call from being deleted with it.
- **`entity_id` is the merchant's PUBLIC id and has no foreign key**: the
  reference is registered before the merchant row exists (the answer decides the
  registration), so a refused registration leaves a sync naming no row — which
  is exactly what makes the loop remove it.
- **`merchants.avatar_withheld` keeps the avatar instead of clearing it** for a
  file its owner can bring back (trash, private). Deleted, blocked and permanently lost files clear
  `avatar_file_id`. `merchants_avatar_withheld_needs_avatar_check` refuses a
  withheld nothing. `avatar_file_event_at` orders Oxy's unordered events and is
  reset to the write time whenever the avatar changes, so an event about the
  file from before it was set again is ignored.
- **`oxy_file_events` is pruned after 45 days** by the reconciliation loop: Oxy
  expires an undelivered event after 30, so an older row dedupes nothing.
  `merchant_avatar_audit.event_id` therefore carries no foreign key to it.

### Files (`files`) and dispute evidence

- **A File is never deleted and never re-pointed.** Submitted evidence and the
  merchant's logo reference it; what Oxy says afterwards is its standing:
  `withheld` (reversible) or `removed_at`/`removed_by` (final) —
  `files_removed_agrees_check` makes the pair one fact and
  `files_removed_not_withheld_check` keeps a removed file from reading as
  withheld. `oxy_file_event_at` orders Oxy's unordered events, as
  `merchants.avatar_file_event_at` does.
- **The purpose is part of the reference.** `dispute_evidence_files` points at
  `files (id, merchant_id, purpose)` with a `file_purpose` pinned to
  `dispute_evidence` by a CHECK, so another merchant's file — or the merchant's
  own identity document — cannot be attached by naming its id.
  `merchants_business_logo_file_fkey` points at `files (id, merchant_id)`; the
  logo's purpose is the one writer's check (`applyMerchantPatch`).
- **The size CHECK is the largest purpose's ceiling**; per-purpose type and size
  are the upload's one writer (`services/files.ts`, `FILE_PURPOSE_POLICIES`).
- **`dispute_evidence_files` holds ids, never words.** The draft text is at the
  provider; `disputes.has_evidence` is the provider's boolean answer.

### Payment method breadth

- **`payment_method_configurations.preferences` holds only explicit choices**
  (`{type: 'on'|'off'}`), merged in SQL (`||`), so a default Orbit changes later
  reaches every merchant who never chose. It never holds `faircoin`: FairCoin is
  locked on (ADR 0021 D2) and its entry is computed from the merchant's key. `version` moves with every change and
  is the compare half of `payment_method_configuration_bindings.synced_version`,
  which only moves forward (`greatest`).
- **One default per merchant** is a partial unique index (`… where is_default`),
  which is also what converges two racing lazy creates;
  `…_default_is_active_check` keeps the default usable.
- **`payment_intents.payment_method_types` is fixed at creation** and checked
  against the card-rail set; `payment_intents_payment_method_types_rail_check`
  is one-directional (`rail = 'card' or types is null`) on purpose: rows from
  before breadth hold none until the post-phase backfill (`0051`), and the
  outgoing image keeps writing them without during the rollout.
- **`payment_method_domains`** is unique per `(merchant_id, domain_name)` and per
  `(provider, provider_object_id)`: one provider account per mode registers a
  domain once, so a second merchant naming it is refused rather than sharing
  wallets. The domain CHECK is the writer's hostname rule.

## Events and webhook endpoints (ADR 0014 D4)

`events`, `webhook_endpoints` and `webhook_deliveries` (`schema/events.ts`,
`schema/webhooks.ts`). Decisions a reader would otherwise undo:

- **One writer, in the change's transaction.** `recordEvent`
  (`services/events.ts`) inserts the event and its deliveries together; the
  event is the record whether or not any endpoint wants it.
- **The event is a snapshot.** `data_object` is the object as rendered under
  `api_version`; deliveries carry no body and render the event at attempt time,
  so every attempt and redelivery sends the same object.
- **`livemode` is not a column** on any of the three (ADR 0017): each reads its
  merchant's in the row's own statement.
- **`events_intent_event_has_intent_check`** moved here from
  `webhook_deliveries`, still keyed on the declared scope
  (`WEBHOOK_EVENT_SCOPES`), not on a name prefix: the row is written inside the
  money transaction.
- **`webhook_endpoints_enabled_events_check`** is `<@ ARRAY[…]` over
  `WEBHOOK_ENABLED_EVENTS` — every subscribable type and `*`, never the targeted
  `webhook_endpoint.test` — so a type cannot be subscribed that the catalog
  does not hold.
- **`webhook_endpoints_secret_check` is only "non-empty".** A generated secret
  is `whsec_` + 64 hex, but the endpoints migrated from `merchants.webhook_secret`
  keep the merchant's value byte for byte so their receivers keep verifying.
- **`(previous_secret IS NULL) = (previous_secret_expires_at IS NULL)`** and
  **`(status = 'disabled') = (disabled_reason IS NOT NULL)`**: each pair is one
  fact. The previous secret is only USED while its expiry is in the future,
  judged by the database clock in `findEndpointSigningTarget`.
- **The endpoint cap (16) is not a CHECK**: `insertEndpoint` locks the merchant
  row and counts, so two concurrent creates cannot both pass at fifteen.
- **The failure run is one statement** (`recordEndpointAttempt`): the
  comparison with the three-day bound and the disable happen in the same
  `UPDATE`, gated on `status = 'enabled'`.
- **Retention is `@oxy.so/db/expiry`** on `events.created_at`
  (`services/eventSweeper.ts`, 30 days), and every API read filters on the same
  horizon, so correctness does not wait on the sweep.
- **Migration `0040`/`0041` hand-build uuid v7 ids** (`pg_temp.peable_uuid7`)
  for the backfilled rows, from the original instant, so the keyset walk keeps
  creation order — a v4 from `gen_random_uuid()` would sort them randomly.

## Generic idempotency (ADR 0014 D3)

`idempotency_keys` (`schema/idempotency.ts`) holds one row per merchant and
`Idempotency-Key`: the request it is bound to (method, path, sha256 of the
canonical JSON body), a lease while that request runs, and then the status and
body it answered. Decisions a reader would otherwise undo:

- **It sits in FRONT of business idempotency, never instead of it.**
  `payment_intents (merchant_id, idempotency_key)` and the `external_ref` of
  refunds, transfers and reversals still decide whether money moves twice; they
  are durable where this row lives 24 hours, and they absorb a lease takeover.
- **One statement claims the key** (`claimIdempotencyKey`): `insert … on
  conflict do update … where` the row is expired, or its lease ran out for the
  SAME request. A read-then-insert would let two first requests both run.
- **`id` names the claim, not the key.** A takeover rotates it, so a request
  that outlived its lease completes or releases nothing (`where id = …` no
  longer matches) — the compare half of the write.
- **CHECKs**, each against the one writer: the key pattern (`^[ -~]{1,255}$`,
  the header's own rule), the request hash shape, `method in ('POST')`,
  `response_status between 200 and 499` (a 5xx is never stored — the row is
  deleted so the caller can retry), `completed ⇔ a response`, and `in_progress
  ⇔ a lease`.
- **Every instant is the database's `now()`**, because the lease is compared
  across tasks whose clocks may disagree.
- **Retention is `@oxy.so/db/expiry`** (`services/idempotencySweeper.ts`), on the
  indexed `expires_at`. Correctness does not wait on it: the read ignores an
  expired row and the claim takes one over.


## FairCoin keys (ADR 0002, amended 2026-11-06)

- **Every reserved address records the key it was derived from**, as lowercase
  hex of the DID's `#key-1` (`IDENTITY_PUBLIC_KEY_PATTERN`, compressed or
  uncompressed secp256k1): `payment_intent_outputs.identity_public_key`,
  `payment_intents.faircoin_identity_public_key` (output 0, beside `address` and
  `faircoin_recipient_account_id`) and `social_send_attributions.identity_public_key`.
- **Nullable, and no CHECK requires it.** Rows written before have none, and a
  `NOT VALID` CHECK is still enforced on every UPDATE — a status transition of
  one of those rows would be refused. The CHECKs only bound the spelling (and
  the rail on `payment_intents`).
- **`payment_intents.faircoin_recipient_key_replaced_at`** is written only by
  `updateIntentState` (`recipientKeyReplaced`), as `coalesce(existing, now())`
  in the transition's own statement: set once, never cleared — a reorg's
  `succeeded → processing` keeps it.
- `recipient_key_changed` widens `payment_intents_cancellation_reason_check`.
- Migrations: `0099` (pre) the hot `payment_intents` DDL alone — two nullable
  columns, no default, its CHECKs and the widened reasons re-added `NOT VALID` by
  hand; `0100` (pre) the outputs' and attributions' columns, CHECKs `NOT VALID`;
  `0101` (post) validates them.

## Payments core (ADR 0019)

- **`payment_intents` statuses are Stripe's seven**; `CARD_ONLY_STATUSES`
  (`requires_payment_method`, `requires_confirmation`, `requires_capture`) are
  refused on the chain by `payment_intents_card_statuses_are_card_check`, and
  the card-only fields (`payment_method_id`, `setup_future_usage`,
  `capture_method = 'manual'`, `statement_descriptor_suffix`) by
  `payment_intents_card_only_fields_check`.
- **`canceled_at` ⇔ `status = 'canceled'`, and `cancellation_reason` only on a
  cancelled row** (`payment_intents_canceled_agrees_check`). The one writer is
  `updateIntentState` (and the sweeper's claim), which stamps both in the
  transition's own statement.
- **`amount_received` is stored, `amount_refunded` is not.** The first is a fact
  of the transition (a partial capture receives less) and is `'0'` outside
  `succeeded` (`payment_intents_amount_received_agrees_check`); the second is
  the sum of succeeded refunds, read in the same statement as the row — the
  refund rows are its one home.
- **A scalar subquery in a column map that every RETURNING shares must be
  table-qualified in raw SQL.** drizzle renders column references UNqualified in
  `INSERT/UPDATE … RETURNING`, and an unqualified `"id"` inside a subquery over
  `charges` or `refunds` binds to THAT table's `id` — a silently wrong answer,
  not an error. `latestChargePublicId` and `amountRefunded` are written with
  `"payment_intents"."id"` for that reason (measured).
- **`charges`: one per payment intent** (`charges_payment_intent_id_key`),
  written by `ensureChargeForIntent` in the transition's transaction; `outcome`
  and `payment_method_details` are a provider snapshot, NULL until read.
- **`customers` are tombstoned, never deleted** (`deleted_at`): payment intents
  and payment methods reference them with `restrict`. `payment_methods` and
  `payment_intents` reference a customer through `(customer_id, merchant_id)`,
  so a row can only name its own merchant's customer; the customer's default
  method references `(default_payment_method_id, id) → payment_methods (id,
  customer_id)`, so it can only be one of its OWN attached methods — detaching it
  clears the default first, in the same transaction.
- **`customer_provider_bindings` hold the provider customer** — the binding of
  ADR 0016 D2, never serialized, one per (customer, provider); its mode is the
  merchant's (ADR 0017).

## Catalog (ADR 0018)

`products`, `prices`, `coupons`, `coupon_products` and `promotion_codes`
(`schema/catalog.ts`). Decisions a reader would otherwise undo:

- **No provider binding.** A catalog row is Orbit's decision; a provider sees
  only the amounts an invoice or a payment derives from it.
- **Same-merchant references are composite.** `prices (product_id, merchant_id)
  → products (id, merchant_id)`, `promotion_codes (coupon_id, merchant_id) →
  coupons`, `(customer_id, merchant_id) → customers`, and both halves of
  `coupon_products`, so no row can name another merchant's object.
- **A product's default price is one of its OWN prices**: `(default_price_id,
  id) → prices (id, product_id)` — a cycle with `prices.product_id`, which
  drizzle-kit resolves by emitting both foreign keys after both tables.
  `MATCH SIMPLE` switches it off while the product has none. The two table
  callbacks carry an explicit `PgTableExtraConfigValue[]` return type, without
  which `tsc` cannot type the cycle.
- **A price's shape is CHECKs** (`prices_billing_scheme_shape_check`,
  `prices_recurring_check`, `prices_transform_quantity_check`): per-unit ⇔ an
  amount, tiered ⇔ tiers and a mode, recurring ⇔ interval + count + usage type
  (≤ three years), a transform only on per-unit. The TIER amounts live in
  `prices.tiers` (jsonb) and are validated by the one writer
  (`services/catalog/params.ts`), not by a CHECK.
- **Immutability is a chokepoint, not a trigger.** `insertPrice` is the only
  statement that sets a price's amount or shape and `updatePrice` names only
  `active`, `nickname`, `metadata`, `lookup_key`, `tax_behavior`; the service
  refuses a set `tax_behavior` moving.
- **The lookup key is decided by the unique index**
  (`prices_merchant_lookup_key_key`, partial): an insert is `ON CONFLICT DO
  NOTHING`, an update runs under a savepoint and maps the violation, so two
  concurrent claims cannot both win and the loser's transaction survives to
  answer 400.
- **Coupon ids are per MERCHANT and forever.** `coupons_merchant_public_id_key`
  covers deleted (tombstoned, `deleted_at`) coupons too, so a promotion code or
  a future discount naming a coupon cannot be re-pointed at new terms.
  `percent_off_bps` is basis points — the discount is integer math.
- **`coupon_products` is `restrict` both ways.** A cascade that removed the last
  row would turn a restricted coupon into one that applies to everything.
- **A promotion code is unique among ACTIVE codes, case-insensitively**
  (`promotion_codes_merchant_active_code_key` on `(merchant_id, lower(code))
  WHERE active`), Stripe's rule; reactivation contends for it like a create.
- **Locks are taken product → price** (`updateProduct`, `updatePrice`,
  `createPrice`, `deleteProduct`), so archiving a default price and changing the
  default cannot interleave, and a price cannot be created on a product being
  deleted.
- **Every scalar subquery in a catalog column map is raw, aliased and
  table-qualified**, for the RETURNING reason above: an unqualified `"id"` in
  the `applies_to` subquery bound to `products.id` and answered `null` for every
  restricted coupon (measured).
- **Migrations `0046`/`0047`.** New tables, plus `events_type_check` and
  `webhook_endpoints_enabled_events_check` widened for the ten catalog event
  types — re-added `NOT VALID` by hand in `0046` and validated in `0047`
  (`post`), so the ACCESS EXCLUSIVE lock on `events` never scans.

## Request logs and the live tail

`api_request_logs` (`schema/requestLogs.ts`) holds one row per answered,
service-authenticated merchant `/v1` request (`lib/requestLog.ts`, the one
writer). Decisions a reader would otherwise undo:

- **What it holds is the whole list**: method, path without its query string,
  status, duration, `Idempotency-Key`. Never a body, a header, a query string or
  an address — the merchant reads this log back, so it must not hold what a
  request carried. `api_request_logs_path_check` refuses a `?`.
- **`request_id` is the public id** (the `Request-Id`, `req_…`), unique, and
  in the id-column ledger as the row's own identifier.
- **Written after the answer, outside any business transaction**: a failed
  write never changes what the merchant was told.
- **`cascade` from the merchant**, as `idempotency_keys`; `livemode` is not a
  column (ADR 0017).
- **Retention is `@oxy.so/db/expiry`** on the indexed `created_at`
  (`services/requestLogSweeper.ts`, 30 days); every read filters on the same
  horizon.
- **The live tail is a `NOTIFY` on the writing transaction**
  (`services/liveTail.ts`): `recordEvent` and the request-log writer signal
  `peable_test_events` / `peable_test_request_logs` with `merchant_id:row_id`
  for a TEST-MODE row only, so a stream hears of a row at its commit and never
  of a rollback, and live commits never take the notify queue's lock. The
  stream reads the row back through its repository; the payload is never a copy.

## Search and report runs (Orbit Phase 8)

`report_runs` (`schema/reporting.ts`), `charges.billing_details`, and the
indexes the search walks. Decisions a reader would otherwise undo:

- **No search extension.** No `pg_trgm`, no `tsvector`: substring is
  `strpos(lower(col), lower($1))` over the merchant's rows, equality on text is
  `lower(col) = lower($1)`, metadata is `@>` containment (a GIN index would
  serve it unchanged, if one is ever clearly needed).
- **The walk indexes are `(merchant_id, id)`**: every list and search is
  `merchant_id = … order by id desc limit n`, so the index is the walk and a
  page reads `n` rows. Added where a table had no merchant index (`charges`,
  `refunds`) and on the hot `payment_intents` (`0063`, alone, `IF NOT
  EXISTS`); `customers (merchant_id, lower(email))` serves the
  case-insensitive email search. `routes/__tests__/search.realdb.test.ts` proves
  each is usable with `enable_seqscan = off`.
- **A run's result is its own merchant's report file**:
  `(result_file_id, merchant_id, result_file_purpose) → files (id,
  merchant_id, purpose)`, the purpose pinned to `finance_report_run` by a
  CHECK — the `dispute_evidence_files` rule.
- **Its lifecycle is CHECKs**: succeeded ⇔ a result and `succeeded_at`,
  failed ⇔ `error`, only a pending run holds a lease (`lease_token` and
  `lease_expires_at` together). The claim is one `UPDATE … where id = (select …
  for update skip locked)`; completion and failure are gated on the claim's
  `lease_token`, so a worker that outlived its lease writes nothing. A deferral
  moves the lease forward rather than clearing it — the backoff needs no column.
- **`finance_report_run` widens `files`**: the purpose, the `csv` type and the
  64 MiB ceiling (`files_size_check`). The upload cap is computed over
  `FILE_UPLOAD_PURPOSES` only, so the widening never raised what `POST
  /v1/files` accepts.
- **Migrations `0062`–`0064`.** `0062` re-adds every widened CHECK on an
  existing table `NOT VALID` by hand and `0064` (post) validates them.

### Report schedules (`0117`–`0118`)

- **One run per occurrence is a unique index, not a read.**
  `report_runs_schedule_occurrence_key (report_schedule_id, scheduled_for)`:
  the scheduler's lease keeps two tasks off one schedule, and this keeps a
  claimer whose lease lapsed from inserting a second run if it ever reaches
  the insert. `(report_schedule_id is null) = (scheduled_for is null)`; a
  direct run has neither, and NULLs never collide in the index.
- **A run names its schedule within its merchant**: `(report_schedule_id,
  merchant_id) → report_schedules (id, merchant_id)`, the composite rule of the
  result file.
- **`next_run_at` exists exactly while `active`**
  (`report_schedules_next_run_agrees_check`): a paused or canceled schedule
  cannot be due, so no claim predicate has to remember the status twice;
  canceled ⇔ `canceled_at`; only an active schedule holds a lease.
- **The anchor CHECK is the interval's**: weekly ⇔ `weekly_anchor`, monthly ⇔
  `monthly_anchor` (1–31; the calendar clamps to a shorter month, so 31 is
  legal and fires on the 30th or the 28th/29th).
- **The time zone is checked by the API, not a CHECK**: Postgres has no zone
  list a CHECK could read without a function call; the column is bounded to 64
  characters and `isKnownTimeZone` (`scheduleCalendar.ts`) refuses the rest.
- **The last run is not stored.** It is the newest run naming the schedule (a
  scalar subquery over the occurrence index), so no second writer can leave it
  stale.
- **`customer_emails.report_run_id`** names the run a `report_run_succeeded` /
  `report_run_failed` email is about (the subject CHECK, widened `NOT VALID`
  with the kind CHECK and the foreign key in `0117`, validated in `0118`). One
  row per recipient, deduplicated by `<kind>:<run>:<recipient, lower-cased>`.

## Orbit money (ADR 0015)

`fee_schedules`, `application_fees`, `application_fee_refunds`, `payouts`,
`balance_transactions`, `ledger_entries` and `reconciliation_mismatches`
(`schema/money.ts`), plus `connected_accounts.role` and the destination-charge
fields on `payment_intents`. Decisions a reader would otherwise undo:

- **The merchant's own account is a `connected_accounts` row**, not a new
  table: `role = 'merchant'`, `(role = 'merchant') = (external_ref IS NULL)`,
  card half only (`connected_accounts_merchant_role_is_card_check`), one per
  merchant (`connected_accounts_merchant_role_key`, partial). A second table
  would give one provider-account kind two snapshot writers and two refresh
  paths. Requirement COUNTS became identifier LISTS (`currently_due` …), the
  counts dropped post-deploy.
- **Ledger amounts are SIGNED** (`SIGNED_BASE_UNIT_STRING_PATTERN`, no `-0`): a
  refund or payout takes money out. Every other money column keeps the
  non-negative pattern.
- **`balance_transactions.fee` and `.net` are NULL together**, and when known
  `amount - fee = net` (`balance_transactions_net_agrees_check`) — the
  provider's own arithmetic, restated where a writer cannot break it.
- **`informational` ⇔ FairCoin ⇔ no provider**
  (`balance_transactions_informational_agrees_check`): coins Orbit never held
  can never sit in a payable balance.
- **Idempotent ingestion is `ingestion_key`** (`<provider>:<provider id>`, or
  `faircoin:<intent>:<n>` for the n-th informational row of a payment, so a
  reorg's reversal and a re-confirmation are distinct rows).
- **The zero sum is not a CHECK** — it spans rows. `postJournal` refuses an
  unbalanced journal before inserting; `ledger_entries_transaction_kind_balance_type_key`
  makes a journal of each kind post once per transaction; the reconciliation
  re-proves the sum (`unbalanced_journal`).
- **`source_type` / `source_id` have no foreign key**: the source is one of six
  tables by public id, and a provider source Orbit never saw is a legitimate
  NULL.
- **Every reference into an account is `(connected_account_id, merchant_id)` →
  `connected_accounts (id, merchant_id)`** — the account is the row's own
  merchant's, the companion-reference rule of ADR 0001 D6.
- **A payout instruction is a row before it is a provider object**
  (`provider_object_id` NULL, unique where set), the two-step every money
  movement uses; `automatic ⇔ origin = 'provider'`, and a provider-origin row
  always has its object.
- **`reconciliation_mismatches` keeps one OPEN row per (kind, subject)**
  (partial unique); `subject` is a provider id or a journal id and is never
  serialized.
- **The hot-table DDL is split** (`0053` merchants, `0054`/`0055`
  connected_accounts, `0056` payment_intents; `0052` the new tables), every constraint added to an
  existing table is `NOT VALID`, and the post migration validates them and drops
  the requirement counts.


## Checkout v2 (Orbit Phase 3)

`checkout_sessions` (now an order), `checkout_session_line_items`,
`payment_link_line_items`, the new `payment_links` options, `merchant_branding`,
`merchant_email_settings` and `customer_emails` (`schema/payments.ts`,
`schema/checkout.ts`). Decisions a reader would otherwise undo:

- **`checkout_sessions.amount` is `amount_total`.** The column kept its name so
  the image that predates the order model kept serving through the rollout;

  (`checkout_sessions_amounts_check`).
- **`payment_intent_id` is nullable**: an open session has no payment until the
  payer confirms. The unique index still makes a payment one session's (NULLs

  without a payment and a payment session without a SetupIntent.
- **One fact per pair**: `complete` ⇔ `completed_at`, `expired` ⇔ `expired_at`
  (`checkout_sessions_status_instants_check`); `no_payment_required` is setup's,

  the payer changes is re-priced by the same rule even if the catalog price is
  archived meanwhile. Prices are immutable, so for a catalog line the snapshot
  IS the price. Its bounds are a CHECK: a non-adjustable line has none and
  quantity ≥ 1; an adjustable one sits inside its own minimum and maximum.
- **Same-merchant references are composite** — line → `prices (id,
  merchant_id)` and `products`, session → `customers`, `coupons`,
  `promotion_codes (id, merchant_id)`. The two new unique targets
  (`prices_id_merchant_id_key`, `promotion_codes_id_merchant_id_key`) were moved
  above their foreign keys by hand (§Composite foreign keys).
- **Only contribution links keep an amount** (`payment_links_amount_shape_check`);
  a price link's amounts are its lines'. Pre-Phase-3 price links were migrated
  to one product + one one-time price + one line each (no catalog events: nothing
  happened to them now), and `success_url` became `after_completion` before the
  column was dropped.
- **A link visit's operation key is unique per link**
  (`checkout_sessions_link_operation_key`): the contribution's write-before-
  network UUID returns the session it created, under a race too.
- **The receipt counter is the derivation index's pattern**:
  `merchant_email_settings.next_receipt_number`, claimed by one upsert
  `RETURNING n - 1`.
- **`customer_emails.dedupe_key`** (`<kind>:<subject id>`) is the outbox's
  idempotency; `customer_emails_subject_check` makes each kind name exactly its
  subject, and a receipt its number.
- **Migrations `0058`–`0061`.** `0058` the new tables and `payment_links`
  (every CHECK on an existing table `NOT VALID`); `0059` `checkout_sessions`'
  hot-table DDL alone (FKs and CHECKs `NOT VALID`); `0060` its indexes `IF NOT
  EXISTS`; `0061` (post) the data — pre-Phase-3 sessions get a client secret,
  their payment's deadline and status and one line; price links their catalog
  rows — then every `VALIDATE`, then the generated `DROP COLUMN success_url`.

`customer_balance_transactions`, `billing_settings`, `test_clocks`,
`billing_meters`, `billing_meter_events`, `entitlement_features`,
`product_features`, `customer_entitlement_summaries`,
`billing_portal_configurations`, `billing_portal_sessions`
(`schema/billingEngine.ts`, `testClocks.ts`, `meters.ts`), plus `customers.balance
/ currency / test_clock_id` and `prices.meter_id`. Decisions a reader would
otherwise undo:

- **Statuses move only by CAS** — `setSubscriptionStatus` / `setInvoiceStatus`
  (`status = from` in the WHERE), reached only from `transitions.ts`. Every
  other write goes through the `…Patch` functions, which cannot name `status`.
- **SIGNED amounts** carry `SIGNED_BASE_UNIT_STRING_PATTERN`
  (`^(0|-?[1-9][0-9]*)$`: no `+`, no `-0`): a line's `amount` and
  `discount_amount` (a credit's discount has the credit's sign), an invoice's
  `subtotal`, `total_discount`, `tax`, `total`, `total_excluding_tax`,
  `starting_balance`, `ending_balance`, a customer's `balance` and a balance
  transaction's `amount`/`ending_balance`. Everything a payer is ASKED for
  (`amount_due`, `amount_paid`, credit-note totals) is unsigned.
- **A negative invoice item is a proration** (`invoice_items_amounts_check`):
  `createInvoiceItem` refuses a negative amount, so a merchant credit is a
  credit note or a balance transaction, never a hand-made negative item.
- **Finalized means numbered**: `invoices_finalized_check` makes `number`,
  `hosted_token`, `finalized_at` and `ending_balance` exist exactly from `open`
  on, and `invoices_automatic_tax_check` refuses a non-draft taxed invoice
  whose `automatic_tax_status` is not `complete` — an invoice cannot leave
  draft untaxed even if code tried.
- **The invoice counter is in `billing_settings`**, taken by one `UPDATE …
  RETURNING next_invoice_number - 1` inside the finalize transaction (the
  derivation index's pattern): row-locked, `integer` for §Counters' reason, and
  gapless because a rollback returns the number. `invoices_merchant_number_key`
  (partial, numbered rows) is the backstop.
- **One engine invoice per subscription period**:
  `invoices_subscription_period_reason_key` on `(subscription_id,
  billing_reason, period_start)` for `subscription_create`/`subscription_cycle`
  — the insert is `ON CONFLICT DO NOTHING`, so a second worker renewing the
  same period writes nothing. Proration and cancel invoices are outside it.
- **Same-merchant references are composite** (`(customer_id, merchant_id) →
  customers`, `(price_id, merchant_id) → prices` — which is why `prices` gained
  `prices_id_merchant_id_key`, hand-moved above the foreign keys in the
  migration); a subscription's and an invoice's default method is one of the
  CUSTOMER's (`(default_payment_method_id, customer_id) → payment_methods`), a
  subscription's latest invoice one of ITS invoices (`(latest_invoice_id, id) →
  invoices (id, subscription_id)`, a cycle drizzle-kit emits after both
  tables), and an invoice's subscription the same customer's.
- **FairCoin cannot be debited, as a CHECK**:
  `subscriptions_faircoin_sends_invoices_check` and
  `invoices_faircoin_sends_check` (`currency <> 'FAIR' or (send_invoice and no
  default method)`).
- **`test_clock_id` is copied** from the customer onto its subscriptions and
  invoices, so the scheduler's claim is one join to `test_clocks`; a customer's
  clock never changes. The claim's `coalesce(tc.frozen_time, now())` is the
  injected clock (ADR 0018 §3) in SQL. Test-mode-only is the service's check
  (a CHECK cannot read the merchant's mode).
- **`next_action_at` + `lease_expires_at` are the scheduler** — partial indexes
  on `next_action_at is not null`; no job table to drift from the rows.
- **Ordered ids for lines and invoice items** (`orderedId`): a uuid v7 is
  ordered only to the millisecond, and a credit and its replacing charge are
  written within one; lines are read back in key order, so their ids are
  minted strictly increasing per process.
- **Meter events are idempotent forever** by `(merchant_id, identifier)`; one
  ACTIVE meter per event name (`billing_meters_merchant_active_event_key`,
  partial); `prices_recurring_check` gained `metered ⇔ meter_id`.
- **Entitlement summaries are the compare half** of
  `entitlements.active_entitlement_summary.updated`: the event is recorded only
  when `customer_entitlement_summaries.feature_ids` moves (row-locked).
- **A portal session stores only its token's SHA-256** (`token_hash`), never
  the bearer token; an invoice's `hosted_token` is stored (it is re-rendered
  into `hosted_invoice_url` on every read, like a payment link id).
- **Invoice emails ride Orbit's ONE email outbox** (`customer_emails`, kinds
  `invoice` and `invoice_payment_failed`, `invoice_id`): owed in the change's
  transaction, sent by the dispatcher; `invoice.sent` is recorded only when the
  relay accepted the email.
- **The Stripe-Billing proxy's tables are gone** (`0080`–`0082`, post, ADR
  0018 §7 as built): its bindings, operations, renewal taxes, migration record,
  recurring mirrors and outbox, the FX-quoted FairCoin rail's three tables,
  the adoption columns on `subscriptions` and `provider_events.retry_after`.
  Every one was empty in production. Do not rebuild a provider-billed
  subscription table beside the engine.
- **Migrations `0065`/`0066`**. `0065` is `pre`: new
  tables, additive columns, and the constraints added to EXISTING tables
  (`customer_emails_invoice_fkey`, `customer_emails_kind_check`,
  `customer_emails_subject_check`, `customers_test_clock_fkey`,
  `customers_balance_check`, `prices_meter_fkey`,
  `prices_recurring_check`, `events_type_check`,
  `webhook_endpoints_enabled_events_check`) re-added `NOT VALID` by hand;
  `0066` (`post`) validates them.
- **Quotes (`quotes`, `quote_line_items`, ADR 0018 §5).** `status` is written
  only by `setQuoteStatus` (CAS) through `transitionQuote`. The CHECKs pin
  what a status implies: a `number` and `finalized_at` exist together
  (`quotes_finalized_check`; an `open` or `accepted` quote has them, a
  cancelled DRAFT does not), `accepted_at` ⇔ `accepted` and `canceled_at` ⇔
  `canceled`, `invoice_id`/`subscription_id` only on an accepted quote and
  `invoice_id` always on one (a recurring quote links its subscription's FIRST
  invoice), `amount_tax` NULL only on a draft (or a cancelled draft) with
  automatic tax, and `FAIR` ⇒ `send_invoice`. Every reference is composite with
  `merchant_id`, so a quote cannot name another merchant's customer, coupon,
  promotion code, invoice or subscription. Lines are rewritten WHOLE when a
  draft's lines change (new `li_…` ids), which is what lets finalize prove the
  draft it priced is the draft it freezes (a digest of the lines' public ids,
  prices and quantities). `quote_line_items.price_id` is a catalog price,
  never a snapshot: a price never changes what it charges. The quote counter is
  `billing_settings.next_quote_number`, claimed by ONE upsert
  (`claimQuoteNumber`, which also creates the settings row) in the finalize
  transaction. Expiry has no `next_action_at`: the scheduler reads
  `quotes_open_expires_at_idx` (partial on `open`) and judges "due" on each
  row's own clock. Migrations `0115` (`pre`; `billing_settings_next_quote_number_check`,
  `events_type_check`, `invoices_billing_reason_check` (`quote_accept`) and
  `webhook_endpoints_enabled_events_check` re-added `NOT VALID` by hand) and
  `0116` (`post`, validates them).

## Tax business compliance (ADR 0020)

- **Nothing here is read by the calculator.** `tax_registration_declarations`
  is what the owner SAYS about an authority; `tax_registrations` (ADR 0011) is
  what Peable collects under. A declaration's `collection_registration_id`
  only points at the latter; no write flows through it in either direction.
- **A declaration's dates follow its status**, by CHECK: `registered` and
  `ended` carry `effective_from`, `ended` carries `effective_to`, and an end
  follows its start. `unknown` may carry neither — it is an answer, not a gap.
- **A document is the merchant's own `tax_document` File, structurally**:
  `(file_id, merchant_id, file_purpose)` references `files (id, merchant_id,
  purpose)` with the purpose pinned by CHECK — the `dispute_evidence_files`
  pattern. `file_id` is unique: one file is one document, so a retried attach
  answers the same document.
- **One OPEN review item per finding**: `tax_review_items_open_key` is a partial
  unique index on `(merchant_id, dedupe_key) where status = 'open'`, and the
  upsert is ONE statement, so two concurrent assessments still leave one item.
  Open ⟺ undecided ⟺ no decider ⟺ no decision time
  (`tax_review_items_decided_check`); a decision is a compare-and-swap on
  `status = 'open'`.
- **An assessment is frozen**: its `inputs` are stored verbatim beside their
  SHA-256 (`inputs_digest`, 64 hex by CHECK) and the rule set version, so a
  replay re-runs exactly what was judged. Results are written in the creating
  transaction once its review items exist, and never again.
- **The history holds field names and statuses, never values** — no
  registration number, note or document content in `details`.
- Four foreign keys are NAMED by hand: drizzle's generated names exceed
  Postgres' 63-byte identifier limit and would be silently truncated.
- Migrations: `0073` (pre) creates the tables and re-adds the widened
  `events`, `files` and `webhook_endpoints` CHECKs `NOT VALID`; `0074` (post)
  validates them.

## Customer languages

`customers.preferred_locales` (Stripe's `preferred_locales`) and
`checkout_sessions.payer_locale`. Decisions a reader would otherwise undo:

- **`text[]`, `NOT NULL`, default `'{}'`** — the wire's empty list, never a
  NULL that means the same thing; a constant default keeps `ADD COLUMN`
  catalog-only. The CHECK (`customers_preferred_locales_check`) is rendered from
  `CHECKOUT_LOCALES` like the other locale CHECKs: no NULL element, every element
  in the set, at most one per locale. Uniqueness itself is the contract's
  (comparing elements needs a subquery a CHECK cannot hold).
- **The payer's language is its own column, never written over
  `checkout_sessions.locale`.** `locale` is the merchant's setting (`null`
  follows the browser) and is on the wire; rewriting it at confirm would make a
  merchant read back a value it never set and pin the page's language on a
  revisit. `payer_locale` is internal and written once per confirm by a CAS on
  `updated_at` (`recordSessionPayerLocale`), so a session that moved is not
  touched.
- **Checkout fills `preferred_locales` only on a customer it creates**
  (`checkoutCustomerLocales`: the payer's, else the session's). A customer the
  merchant named keeps its own, empty or not.
- **Migrations `0107`–`0109`.** `0107` the customers column and its CHECK `NOT
  VALID`; `0108` `checkout_sessions`' hot-table DDL alone (nullable column, CHECK
  `NOT VALID`); `0109` (post) both `VALIDATE`s.

## Identity verification (ADR 0023)

`verification_sessions` (`vs_…`) and `verification_reports` (`vr_…`,
`schema/identity.ts`). Decisions a reader would otherwise undo:

- **No column for the person, ever.** A session holds the merchant's
  configuration and the provider's verdict; a report holds each check's
  `*_status` and `*_error_code`. Names, dates, numbers, addresses, the document
  type and issuing country, and the provider's image File ids are not stored —
  `verified_outputs` is a live read. `identity.realdb.test.ts` pins the column
  lists and searches every row for the fake provider's personal values; a new
  column is a decision to argue in ADR 0023 first.
- **No `url` / `client_secret` column.** They are the person's single-use
  credentials, passed through on a create and a retrieve.
- **`provider_object_id` is `NOT NULL`**: the session is created at the
  provider before the row (an Identity-less account must leave no row).
- **`has_last_error` beside `last_error_code`** (`verification_sessions_last_error_check`:
  a code implies a failure): a failure whose code Orbit does not know is still
  a failure, rendered with the generic reason, never dropped.
- **`verification_sessions_redacted_holds_no_reference_check`**: once
  `redaction_status` is set, `metadata = '{}'` and `client_reference_id` is
  null. `updateVerificationSessionState` erases both in the statement that sets
  it; `redactVerificationSessionEvents` erases the same two fields in the
  session's stored events (the one update to an `events` row).
- **`last_verification_report` is not a column**: it is the newest report of
  the session, read in the row's statement (a column would make the two tables
  reference each other).
- **A report is recorded once** — `unique(provider, provider_object_id)`,
  insert-or-nothing in `recordVerificationReport`; the composite
  `(verification_session_id, merchant_id)` reference makes "this merchant's
  session" structural.
- **Migrations `0119`–`0120`.** `0119` the two tables and the widened
  `events_type_check` / `webhook_endpoints_enabled_events_check` `NOT VALID`;
  `0120` (post) validates them.
